# 0002. 計劃住在客戶端

[English](0002-plan-lives-in-the-client.md) · [簡體中文](0002-plan-lives-in-the-client.zh-CN.md) · **繁體中文**

- Status: Accepted
- Date: 2026-11-04
- Scope: `frontend/`, `mobile/`, `product/demo/index.html`

## 背景

計劃是某一天的站點序列。每個站點有開始時間、時長、地點和目的。四到五個，從不更多，而整份東西到明天就一文不值。

一天會被編輯很多次。學生早上揭示它，開始跟隨它，上報一節課遲到，換一頓飯，跳過一場講座，撤銷一次替換。每一次都是對一個序列的改動。

計劃也是系統中唯一被修復用來比對的物件。修復會問一個候選站點是否與已提交站點是同一件事，而那個已提交站點只存在於釋出它的客戶端裡。

物理情況還決定了第二個問題。計劃真正起作用的時刻，是學生站在走廊裡，或者在樓與樓之間走路的時候。走廊裡沒有訊號。一個必須先往返一次才能回答「現在做什麼」的設計，回答得太晚。

一個服務上有兩個客戶端：埠 5173 的桌面構建，三個角色，以及埠 5174 的手機構建，學生檢視。

## 決策

計劃是客戶端狀態。它活在瀏覽器標籤頁的記憶體裡，別處沒有。

客戶端持有狀態機。揭曉或編輯這一天時是 `planning`，學生跟隨它時是 `executing`，現實出現偏差時是 `deviated`，正在應用修復時是 `repairing`。

編輯是本地操作。一個手勢產生一次狀態遷移和一條撤銷記錄，沒有網路呼叫。撤銷棧是本地棧，可以反向回放。

唯一與計劃相關的讀取是可用性，在揭示時透過 `GET /api/availability` 讀取一次。此後當天餘下時間都信任這個快照。課表被複制進計劃作為錨點並凍結，所以即使網路消失，錨點依然是牆。

關於計劃的一切都不持久化。`localStorage` 儲存認證令牌、顯示名、角色和語言。它不儲存站點。

修復在客戶端執行，針對的是學生真正看到的那份已提交計劃。服務端不被諮詢，也無法觀察這次修復。

## 後果

每次編輯都是即時的。從一次點選到新計劃之間沒有延遲，這很重要，因為學生改主意時同一個點選可能在一分鐘內重複三次。

服務端不持有會話狀態。它不知道計劃存在，所以無法洩露它、讓它過期，或者因為它而阻塞。

計劃在離線時繼續工作，而離線是常態而不是邊緣情況。一旦這一天被揭示，走廊對計劃能否被讀或修復沒有任何影響。

撤銷是免費的。一個棧覆蓋所有動作，包括規劃者執行的動作，因為它們全都是本地狀態遷移。

計劃不跟隨學生跨裝置。在手機上揭示的一天在桌面上不存在。這一點被接受。兩個客戶端在不同地點不同時間使用，學生很少同時在兩邊持有同一天。

關閉標籤頁會丟掉這一天。重新揭示需要一次可用性讀取和一次填充，所以損失很小但真實。把計劃持久化到 `localStorage` 可以覆蓋這種情況，目前還沒做。

計劃質量無法中心化度量。執行率與每次修復的變更站點數在計劃所在處計算，所以任何彙總都需要一條顯式的上報路徑。

規劃規則存在於兩個客戶端程式碼庫裡。`frontend/` 和 `mobile/` 可能漂移，在一處修好的規則在被複制過去之前並不算在另一處修好。一個共享模組會有幫助，但它不存在。

## 備選方案

**帶樂觀併發的 plans 表。** 一個版本列和一個讀改寫迴圈。已否決。它為一個一天就過期的文件買了同步，而衝突敘事比它想避免的損失更糟。兩臺裝置編輯同一天並不是任何人要的流程。

**服務端計算這一天並返回。** 客戶端請求今天，收到站點。已否決。每次編輯都變成一個往返和一行服務端資料，每條規劃規則的改動都變成一次部署。它在走廊裡失效，而那裡正是產品被使用的地方。

**服務端規劃加本地影子副本。** 中心計算，本地快取，重連時對賬。已否決。重連需要合併規則，合併規則需要版本，結果就是為了一名學生的午飯時間造一個分散式系統。

**把計劃持久化到 `localStorage`。** 便宜，能覆蓋誤關標籤頁。目前還沒采用，因為它也不能覆蓋換裝置，而且它引入一份比它所屬的那天活得更久的陳舊計劃。這是個小補充，不是對本決策的推翻。

**帶重連合並的操作日誌。** 離線優先，按操作對賬。已否決。合併規則會為一個不會發生的情況而發明，而錯誤的合併比丟失的計劃更難被發現。
