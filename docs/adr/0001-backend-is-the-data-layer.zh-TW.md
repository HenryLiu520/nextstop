# 0001. 後端是資料層

[English](0001-backend-is-the-data-layer.md) · [簡體中文](0001-backend-is-the-data-layer.zh-CN.md) · **繁體中文**

- Status: Accepted
- Date: 2026-11-04
- Scope: `backend/`, `db/`, both clients' API surface

## 背景

NextStop 只回答一個問題：這個人應該在哪裡，以及應該在什麼時候移動。
這個答案可以在服務端計算，也可以在客戶端計算。這個選擇決定了後端的存在意義。

系統所需的事實並不是同一類東西。

| 屬性 | 計劃 | 課表 |
|---|---|---|
| 所有者 | 一名學生 | 學校機構 |
| 生命週期 | 一天 | 一個學期 |
| 變更頻率 | 每次會話多次編輯 | 釋出後即固定 |
| 真值 | 一份提案，始終可協商 | 最終結果，不容置疑 |
| 讀寫 | 本地可讀可寫 | 我方只讀 |

課表由數千人共享，由本專案無法控制的教務辦公室釋出，並且在整個學期內為真。計劃屬於一個人，到明天就失效。
這是兩個不同的問題，它們需要兩個不同的歸屬。

同一個房間這個事實，不能因為看的人是兩位而不同。如果桌面客戶端和手機客戶端對 2A 在 10:00 到 11:00 是否被佔用存在分歧，系統裡沒有任何東西能裁決這場爭論。課表必須有一個唯一權威，而計劃不需要這樣的權威。

## 決策

後端是資料層。它回答「我能去哪裡」。

它提供課表、房間、建築、可用性、管理員房間更新、評價、帳號和審計日誌。它執行在 Spring Boot 4.1.1 與 Java 21 之上，資料庫為 PostgreSQL 17，Flyway 遷移從 V1 到 V16。

它不儲存任何計劃。沒有 plans 表，沒有接受計劃的端點，也沒有任何列用來存放計劃。伺服器對學生 14:00 應該在哪裡沒有任何意見。

可用性計算保留在服務端，因為這是兩個客戶端必須一致認同的那一個答案：

```
free(room, date) = blocks(room, date)
                 - blocks taken by a class
                 - blocks taken by an active room update
                 - 10 minutes either side of every occupied block
```

切換餘量是服務端配置，預設 10 分鐘，永遠不是客戶端設定。課表優先於管理員備註：與上課時段重疊的更新會被拒絕，返回 HTTP 400 與錯誤碼 `TIMETABLE_PRIORITY`。

角色順序為 `user < admin < superadmin`，只在服務端強制執行一次。客戶端只隱藏令牌無權使用的東西。

## 後果

共享事實只有一個歸屬。兩個不同版本的客戶端不可能對同一個房間產生分歧，而對於我方只讀的資料，也不需要任何衝突解決。

規劃規則可以在不做遷移的情況下改變。新的站點型別、新的間隔規則、新的修復優先順序都是客戶端改動。資料庫模式不追蹤計劃的形狀，所以計劃變化時它永遠不必跟著變。

服務保持小巧並且可測試。它的介面面就是一個問題加上管理功能，27 個針對真實資料庫的自動化測試覆蓋了它。

代價是伺服器無法回答某個使用者在 14:00 在做什麼。任何需要這個答案的功能，從共享計劃到提醒，都必須在客戶端實現，或者需要一個新的決策。

多裝置同步是另一件事。沒有儲存的計劃就沒有同步，沒有版本列，也沒有 last-write-wins 規則。它也意味著完全沒有答案，在功能存在之前，這是誠實的立場。

計劃質量對伺服器不可見。四個成功指標只在客戶端埋點，所以中心化度量需要一條顯式的上報路徑。

可用性是一個快照。客戶端在揭示時讀取它，服務端不輪詢，之後變滿的房間會留在計劃裡，直到使用者自己上報。這一點被接受，並未被解決。

## 備選方案

**服務端持有計劃。** 一張 plans 表，配套讀寫端點。已否決。它需要一個使用者、一個版本、一條同步規則和一套衝突敘事，而且它依然輸給一臺沒儲存就關機的手機。代價是協調，而計劃壽命太短，付不起。

**薄後端加客戶端課表。** 課表只發一次，讓每個客戶端自己計算可用性。已否決。同一個共享真值有兩套實現，跑在兩個釋出週期上，沒有仲裁者。光切換餘量就會在兩者之間漂移。

**面向前端的後端，每個客戶端一套端點。** 已否決。兩個客戶端共享一份契約更便宜，而按客戶端劃分的介面面只是掩蓋分歧，並不能阻止分歧。

**把後端做成產品。** 規劃端點、已儲存的日子、會話、服務端推薦。已否決。產品的核心主張是系統來決定這一天，而伺服器無法決定一個它看不見使用者在其中的日子。它還會把有意思的邏輯推到網路邊界和一次部署之後。

**作為便利的計劃快取。** 為每個使用者存下最後一次計劃，方便第二臺裝置接上。暫時否決。它為一個只有一天壽命的文件在服務端增加了寫入路徑，而它服務的唯一使用者是那種中午換了裝置的人。
